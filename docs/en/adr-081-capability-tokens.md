# ADR-081 — Capability tokens (full text)

A “flagship” ADR, published in full to show what a decision looks like in this project: the context that made it necessary, the WHAT / WHY / INTERFACE / SECURITY / TEST / ROLLBACK gate, the **limits stated honestly**, the real-world proof, and what remains to be done. This is the decision that moved security from the screen into the kernel: every tool call made by an agent is checked **before its effect** against a token signed by the kernel.

## ADR-081 — Capability tokens: what the kernel grants to a turn is checked on every tool call (audit 07, P1-1)

**Date**: 2026-09-30
**Context**: audit 07 §3.5 and §7.4. A turn's rights were declarative and observed after the fact: `readOnly` relied on a list of toolsets, an empty `allowedWrite` meant “no restriction” (a write outside the working folder was only seen at git verification, when there was one), `denyWrite` was only proven by hashes after execution, and the private-zone boundary only bounded the CHOICE of working folder. Above all, the offensive department's risk floor only held through `enqueueTask`: `hermes -p exploit-analyst chat` or Hermes's cron launched those profiles with all their tools, with neither policy nor approval (07 §3.6). The only existing capability was the approval token (“run this task, this fingerprint, once”).

**Gate**
- **WHAT** —
  1. **Turn capability token** (`src/core/kernel/turn-capability.ts`): `{sub: profile, task, mode: read|write, root: working folder, allow[], deny[], exp (20 min), jti}`, signed **Ed25519** by the kernel. The hook is another process: it only holds the PUBLIC key (`capability.pub`, always derived from the private one) and therefore cannot forge anything. Issued by the hermes-agent executor for every turn (`HERMES_OS_CAPABILITY`): read for a `readOnly` task, the CV toolset and the CEO; write otherwise, bounded to the working folder, to `allowedWrite`, outside `denyWrite`. `capability.issued` event in the ledger.
  2. **Pure decision** (`src/core/kernel/pep.ts`, everything real injected), in order: private zones forbidden to file tools for EVERY profile, with or without a token (including listing a folder that contains them); a token presented but invalid, expired or issued for another profile → refusal; without a token, a **“kernel only”** profile has no tool at all, the others keep their previous behaviour; valid token → read-only means neither `write_file`/`patch` nor `terminal`/`process_manage`/`execute_code`; write means real paths (links and junctions resolved, `~` expanded) inside the working folder, inside `allow` if declared, never under `deny`, never `cross_profile`. The unannounced multi-file mode of `patch` (V4A format) is parsed: its paths count. An unverifiable path refuses.
  3. **Enforcement point** (`src/security/pep-hook.ts`) in both `pre_tool_call` hooks: the egress registry (all profiles) and the browser guard (Iris, red team), after the kill switch and before their own rules. Refusals logged in `security/pep/pep-<day>.jsonl` (profile, tool, code, task — never the arguments).
  4. **Sealed policy** `security/policies/capabilities.json`: `kernelOnly` = the offensive department (5 profiles). A test requires that every SOUL with `risk_floor: high` is listed; if unreadable, the code fallback keeps the same list.
  5. `doctor` “kernel (capabilities)”: policy consistent with the SOULs, public key consistent with the private one, refusals of the last 24 h, and “kernel only” profiles whose hook is still failure-tolerant. `scripts/security/egress-hook.ps1 -FailClosedKernelOnly` (tested on a copy of HERMES_HOME, **not applied** to the real profiles).
- **WHY** — Move from “role + risk + approval” to “this right, on this resource, for this turn”, enforced BEFORE the effect rather than observed afterwards; make the offensive department's floor impossible to bypass by launching outside the kernel; turn the private-zone boundary into a tool-call rule.
- **INTERFACE** — `issueTurnCapability / verifyTurnCapability`, `decideToolCall / toolPaths / canonicalPath`, `enforce / logDenial / readDenials / loadKernelOnly / realPath`; variables `HERMES_OS_CAPABILITY` (turn), `HERMES_CAPABILITY_KEY_FILE` / `_PUB_FILE` / `_POLICY_FILE` (tests and P0-1).
- **SECURITY** — No guarantee of AXE 44 reduced; least privilege, data separation and Red Cell under control are strengthened. Limits stated honestly: (a) the **terminal is not path-bounded** (a command is free text): in write mode it stays allowed and can write elsewhere — the verification afterwards still detects it; only account separation (P0-1) bounds it; (b) a relative path is judged against the token's working folder, whereas Hermes resolves it against the terminal's current directory, which a `cd` can move; (c) the private key is readable by the operator's account until P0-1 (an agent with a terminal could forge a token; not an agent without one); (d) the registry hook is `fail_closed: false`: the PEP refuses on any error it catches, but a process crash or timeout lets the tool through — including for four offensive profiles, until the operator runs `-FailClosedKernelOnly`; (e) these rules apply to Hermes's tools, not to the claude-code and cursor executors; (f) an issued token is not individually revocable by the hook (it expires; the kill switch cuts everything).
- **Intended behaviour change**: an offensive profile launched by hand (`hermes -p red-team-lead chat`) or by Hermes's cron no longer has any tool. Every offensive task goes through Jarvis, the policy and Windows Hello (ADR-032/033/063). A write by a file tool outside the working folder is refused for every kernel task.
- **TEST** — `tests/kernel-capability.test.ts`: token (tampering, expiry, third-party key); pure decisions (modes, scope, name prefix ≠ subfolder, multi-file `patch`, private zones, profiles); policy ↔ SOUL; hooks launched the way Hermes launches them (write inside allowed, outside refused, including through a JUNCTION; read-only; forged, expired, other-profile token; offensive department without then with a token; refusals logged without arguments). Contracts `tests/contract/hermes-hook-payload.test.ts` (payload with `cwd` and `profile`; turn environment passed to hooks in single-profile mode). `npm test` 889/889, Pester 101/101, contracts 24/24. **Real proof** on the isolated instance: a turn of the `coder` profile writes `interieur.txt` in its working folder; its second `write_file`, towards a neighbouring folder, is refused before it happens — the agent reports the message word for word, the file does not exist, the refusal is logged with the task, `capability.issued` is in the ledger.
- **ROLLBACK** — remove the `enforce` call from both hooks (they go back to ADR-079); stop setting `HERMES_OS_CAPABILITY` in the executor (all turns become “outside the kernel” again: only `kernelOnly` and private zones apply); empty `kernelOnly`.

**Left to the operator**: `pwsh -NoProfile -File scripts/security/egress-hook.ps1 -FailClosedKernelOnly` so that the offensive profiles' hook also refuses on failure.
