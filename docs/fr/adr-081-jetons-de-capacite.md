# ADR-081 — Jetons de capacité (texte intégral)

Un ADR « phare », publié en entier pour montrer à quoi ressemble une décision dans ce projet : le contexte qui l'a rendue nécessaire, la porte WHAT / WHY / INTERFACE / SECURITY / TEST / ROLLBACK, les **limites dites honnêtement**, la preuve réelle, et ce qui reste à faire. C'est la décision qui a déplacé la sécurité de l'écran vers le noyau : chaque appel d'outil d'un agent est contrôlé **avant son effet** contre un jeton signé par le noyau.

## ADR-081 — Jetons de capacité : ce que le kernel accorde à un tour est vérifié à chaque appel d'outil (audit 07 P1-1)

**Date** : 2026-09-30
**Contexte** : audit 07 §3.5 et §7.4. Les droits d'un tour étaient déclaratifs et constatés après coup : `readOnly` tenait à une liste de jeux d'outils, `allowedWrite` vide valait « aucune restriction » (une écriture hors du dossier de travail n'était vue qu'à la vérification git, quand il y en avait une), `denyWrite` n'était prouvé que par empreintes après l'exécution, et la frontière des zones privées ne bornait que le CHOIX du dossier de travail. Surtout, le plancher de risque du pôle offensif ne valait que par `enqueueTask` : `hermes -p exploit-analyst chat` ou le cron d'Hermes lançaient ces profils avec tous leurs outils, sans politique ni approbation (07 §3.6). La seule capacité existante était le jeton d'approbation (« exécuter cette tâche, cette empreinte, une fois »).

**Gate**
- **WHAT** —
  1. **Jeton de capacité d'un tour** (`src/core/kernel/turn-capability.ts`) : `{sub: profil, task, mode: read|write, root: dossier de travail, allow[], deny[], exp (20 min), jti}`, signé **Ed25519** par le kernel. Le hook est un autre processus : il ne tient que la clé PUBLIQUE (`capability.pub`, toujours dérivée de la privée) et ne peut donc rien fabriquer. Émis par l'executor hermes-agent pour chaque tour (`HERMES_OS_CAPABILITY`) : lecture pour une tâche `readOnly`, le jeu d'outils CV et le CEO ; écriture sinon, bornée au dossier de travail, à `allowedWrite`, hors de `denyWrite`. Événement `capability.issued` au journal.
  2. **Décision pure** (`src/core/kernel/pep.ts`, tout le réel injecté), dans l'ordre : zones privées interdites aux outils fichiers pour TOUT profil, avec ou sans jeton (y compris fouiller un dossier qui les contient) ; jeton présenté mais invalide, expiré ou émis pour un autre profil → refus ; sans jeton, un profil **« kernel seulement »** n'a aucun outil, les autres gardent leur comportement d'avant ; jeton valide → lecture seule = ni `write_file`/`patch` ni `terminal`/`process_manage`/`execute_code` ; écriture = chemins réels (liens et jonctions défaits, `~` développé) dans le dossier de travail, dans `allow` s'il est déclaré, jamais sous `deny`, jamais `cross_profile`. Le mode multi-fichiers non annoncé de `patch` (format V4A) est lu : ses chemins comptent. Un chemin invérifiable refuse.
  3. **Point d'application** (`src/security/pep-hook.ts`) dans les deux hooks `pre_tool_call` : registre des sorties (tous les profils) et garde du navigateur (Iris, red team), après l'arrêt d'urgence et avant leurs règles propres. Refus journalisés dans `security/pep/pep-<jour>.jsonl` (profil, outil, code, tâche — jamais les arguments).
  4. **Politique scellée** `security/policies/capabilities.json` : `kernelOnly` = le pôle offensif (5 profils). Un test exige que tout SOUL au `risk_floor: high` y figure ; illisible, le repli en code garde la même liste.
  5. `doctor` « kernel (capacités) » : politique cohérente avec les SOUL, clé publique cohérente avec la privée, refus des dernières 24 h, et profils « kernel seulement » dont le hook reste tolérant aux pannes. `scripts/security/egress-hook.ps1 -FailClosedKernelOnly` (testé sur une copie de HERMES_HOME, **non appliqué** aux vrais profils).
- **WHY** — Passer de « rôle + risque + approbation » à « ce droit, sur cette ressource, pour ce tour », appliqué AVANT l'effet et non constaté après ; rendre le plancher du pôle offensif incontournable par un lancement hors kernel ; faire de la frontière des zones privées une règle d'appel d'outil.
- **INTERFACE** — `issueTurnCapability / verifyTurnCapability`, `decideToolCall / toolPaths / canonicalPath`, `enforce / logDenial / readDenials / loadKernelOnly / realPath` ; variables `HERMES_OS_CAPABILITY` (tour), `HERMES_CAPABILITY_KEY_FILE` / `_PUB_FILE` / `_POLICY_FILE` (tests et P0-1).
- **SECURITY** — Aucune garantie de l'AXE 44 réduite ; moindre privilège, séparation des données et Red Cell sous contrôle sont renforcés. Limites dites honnêtement : (a) le **terminal n'est pas borné par chemin** (une commande est du texte libre) : en mode écriture il reste permis et peut écrire ailleurs — la vérification d'après le constate toujours ; seule la séparation des comptes (P0-1) le borne ; (b) un chemin relatif est jugé contre le dossier de travail du jeton, alors qu'Hermes le résout contre le dossier courant du terminal, qu'un `cd` peut déplacer ; (c) la clé privée est lisible par le compte de l'opérateur jusqu'à P0-1 (un agent muni du terminal pourrait se fabriquer un jeton ; pas un agent sans terminal) ; (d) le hook du registre est `fail_closed: false` : le PEP refuse sur toute erreur qu'il attrape, mais un plantage du processus ou un délai dépassé laisse passer l'outil — y compris pour quatre profils offensifs, tant que l'opérateur n'a pas lancé `-FailClosedKernelOnly` ; (e) ces règles valent pour les outils d'Hermes, pas pour les executors claude-code et cursor ; (f) un jeton émis n'est pas révocable individuellement par le hook (il expire ; l'arrêt d'urgence coupe tout).
- **Changement de comportement voulu** : un profil offensif lancé à la main (`hermes -p red-team-lead chat`) ou par le cron d'Hermes n'a plus aucun outil. Toute tâche offensive passe par Jarvis, la politique et Windows Hello (ADR-032/033/063). Une écriture par outil fichier hors du dossier de travail est refusée pour toute tâche du kernel.
- **TEST** — `tests/kernel-capability.test.ts` : jeton (altération, échéance, clé d'un tiers) ; décisions pures (modes, périmètre, préfixe de nom ≠ sous-dossier, `patch` multi-fichiers, zones privées, profils) ; politique ↔ SOUL ; hooks lancés comme Hermes les lance (écriture dedans permise, dehors refusée, y compris par une JONCTION ; lecture seule ; jeton fabriqué, expiré, d'un autre profil ; pôle offensif sans puis avec jeton ; refus journalisés sans arguments). Contrats `tests/contract/hermes-hook-payload.test.ts` (charge utile avec `cwd` et `profile` ; environnement du tour transmis aux hooks en mode mono-profil). `npm test` 889/889, Pester 101/101, contrats 24/24. **Preuve réelle** sur l'instance isolée : un tour du profil `coder` écrit `interieur.txt` dans son dossier de travail ; son second `write_file`, vers un dossier voisin, est refusé avant d'avoir lieu — l'agent rapporte le message mot pour mot, le fichier n'existe pas, le refus est journalisé avec la tâche, `capability.issued` est au journal.
- **ROLLBACK** — retirer l'appel `enforce` des deux hooks (ils reviennent à ADR-079) ; ne plus poser `HERMES_OS_CAPABILITY` dans l'executor (tous les tours redeviennent « hors kernel » : seuls `kernelOnly` et les zones privées s'appliquent) ; vider `kernelOnly`.

**Reste à l'opérateur** : `pwsh -NoProfile -File scripts/security/egress-hook.ps1 -FailClosedKernelOnly` pour que le hook des profils offensifs refuse aussi en cas de panne.
